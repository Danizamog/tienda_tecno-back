📋 Resumen Ejecutivo

Conclusión Principal: Su hipótesis es parcialmente correcta. El backend SÍ está siendo parcialmente omitido, pero el patrón es más complejo que "solo frontend → PocketBase".

Hallazgo Crítico: El archivo .env del backend contiene credenciales de placeholder que no pueden autenticarse contra la instancia de PocketBase en producción. Esto representa un riesgo crítico para las operaciones de escritura.

Patrón Arquitectónico: La plataforma implementa un modelo de dos capas:

  • Operaciones de Lectura (READ): Frontend usa la API Gateway del backend (correcto)
  • Operaciones de Escritura (WRITE): Backend requiere autenticación, pero con credenciales inválidas
  • Archivos/Imágenes: PocketBase directo para archivos, proxy del backend para algunos casos

🔍 Hallazgos Principales

1. Estado de Credenciales de Admin: CRÍTICO ⚠️

Problema Identificado:

El archivo .env del backend contiene credenciales de placeholder:

POCKETBASE_URL=https://tecnotienda.zamoranogamarra.online POCKETBASE_AUTH_IDENTITY=correo@admin.com POCKETBASE_AUTH_PASSWORD=tu_password_admin

Análisis:

  • correo@admin.com - Claramente un placeholder (formato de demostración)
  • tu_password_admin - Literalmente significa "tu_password_admin" en español (credencial de ejemplo)
  • Apunta a PocketBase en producción: https://tecnotienda.zamoranogamarra.online

Impacto:

  • ❌ Los 14 microservicios no pueden autenticarse con PocketBase
  • ❌ Todas las operaciones que requieren token de admin fallarían
  • ❌ Las operaciones de escritura deberían estar bloqueadas en producción
  • ⚠️ El sistema funciona en desarrollo local solo si usa diferentes credenciales

3. Middleware de Autenticación

Patrón Implementado en product-service:

function requireAuth(req, res, next) { const userId = req.headers['x-user-id'] const role = req.headers['x-user-role'] if (!userId || !['vendor', 'admin'].includes(role)) { return res.status(403).json({ error: 'forbidden' }) } next() }

✅ Lo Correcto: Los endpoints de escritura SÍ están protegidos con middleware de autenticación. El backend verifica que solo usuarios con rol 'vendor' o 'admin' puedan crear/modificar/eliminar recursos.

⚠️ El Problema: Esta protección solo funciona SI el backend puede autenticarse con PocketBase usando las credenciales de admin. Con placeholder credentials, el backend no puede funcionar.

4. Inconsistencia en Servicio de Archivos

Hallazgo: Dos Rutas Diferentes para Archivos

El código del frontend muestra dos patrones inconsistentes:

// HomeView.vue - línea 173 ${API}/stores/files/stores/${store.id}/${store.banner} // HomeView.vue - línea 184 ${PB}/api/files/products/${product.id}/${imgs[0]}

Algunos archivos van a través del proxy del backend, otros directamente a PocketBase. Esto dificulta auditar y controlar el acceso a archivos.

🔧 Detalles Técnicos de Hallazgos

Hallazgo #1: Credenciales de Placeholder (CRÍTICO)

Código Afectado:

// Todos los 14 microservicios (product-service, store-service, etc.) const PB_IDENTITY = process.env.POCKETBASE_AUTH_IDENTITY || '' const PB_PASSWORD = process.env.POCKETBASE_AUTH_PASSWORD || '' async function getAdminToken() { const res = await fetch( `${PB_URL}/api/collections/_superusers/auth-with-password`, { method: 'POST', body: JSON.stringify({ identity: PB_IDENTITY, // ❌ 'correo@admin.com' password: PB_PASSWORD // ❌ 'tu_password_admin' }) } ) if (!res.ok) throw new Error(`PB admin auth failed: ${res.status}`) }

¿Por qué es crítico?

  • Todos los servicios llaman a getAdminToken() al iniciar
  • Si la autenticación falla, el servicio falla completamente
  • No hay mecanismo de fallback o degradación
  • Las operaciones de escritura dependen del token de admin

Síntomas Esperados si las credenciales son inválidas:

  • Error HTTP 401 al intentar crear productos
  • Error HTTP 401 al intentar crear órdenes
  • Error HTTP 401 al intentar crear tiendas
  • Los servicios podrían fallar al iniciar si no cachean el error

Hallazgo #2: Imágenes en PocketBase Público (MEDIO)

Ruta Expuesta:

// Frontend ${PB}/api/files/products/${product.id}/${imgs[0]}?thumb=400x400 // Ejemplo real https://tecnotienda.zamoranogamarra.online/api/files/products/abc123/image.jpg

Riesgo: Si alguien enumera los IDs de productos (lo cual es trivial en una API pública), puede descargar todas las imágenes sin autenticación.

Mitigación: Es aceptable porque las imágenes de productos son públicas por naturaleza. Pero deberías implementar:

  • Rate limiting en la ruta de imágenes
  • Validar que el producto existe y está activo antes de servir la imagen

Hallazgo #3: Flujo de Autenticación de Google (OK)

✅ Patente de Seguridad Correcta:

El flujo de Google OAuth está bien implementado:

  1. Frontend obtiene access_token de Google
  2. Frontend envía access_token a /google/sync del backend
  3. Backend valida el token con Google (verifica audience/client_id)
  4. Backend crea/actualiza usuario en PocketBase con token de admin
  5. Frontend recibe registro de usuario sincronizado

✅ Conclusiones y Respuestas a Preguntas

¿El backend está siendo omitido?

❌ PARCIALMENTE NO:

Para operaciones de lectura de datos (productos, tiendas, categorías), el frontend SÍ usa el backend API Gateway. Las imágenes van directo a PocketBase porque son archivos estáticos públicos, lo cual es correcto arquitectónicamente.

⚠️ PERO SÍ para operaciones de escritura: Si las credenciales de admin son inválidas, el backend no puede ejecutar operaciones que requieren acceso de admin, lo que las haría fallar silenciosamente.

¿Por qué el sistema funciona localmente?

Hipótesis más probable:

  • Tienes un archivo .env diferente en tu máquina local con credenciales válidas
  • O tu instancia local de PocketBase tiene configuradas esas credenciales de placeholder
  • O solo estás probando operaciones de lectura (que no requieren credenciales válidas de admin)

¿Qué operaciones realmente necesitan el backend?

Operación Necesita Backend Por qué
Crear producto ✅ Sí Valida que el usuario es owner de la tienda
Listar productos ✅ Sí (pero no requiere login) Filtra por status, categoría, búsqueda
Ver imagen ❌ No Es archivo público, PocketBase lo sirve
Crear orden ✅ Sí Requiere usuario autenticado
Google OAuth ✅ Sí Backend sincroniza usuario a PocketBase

📌 Recomendaciones Inmediatas

1. Resolver Credenciales de Admin (CRÍTICO)

Obtén las credenciales válidas de tu instancia de PocketBase en producción y actualiza el archivo .env. De lo contrario, todas las operaciones de escritura fallarán.

2. Consistencia en Rutas de Archivos (MEDIO)

Define una estrategia clara:

  • Opción A: Todos los archivos a través del backend proxy (más control)
  • Opción B: Todos los archivos directos de PocketBase (más rápido)

Actualmente hay mezcla que dificulta auditoría.

3. Validar Headers de Autenticación

Considera agregar un endpoint backend que valide y genera un JWT firmado en lugar de confiar en headers enviados por el frontend.

4. Rate Limiting en Imágenes

Implementa rate limiting en los endpoints de imágenes de PocketBase para prevenir ataques de enumeración masiva.

5. Documentar Flujos de Datos

Crea un documento que especifique claramente qué endpoints van a través del backend vs. directo a PocketBase. Esto ayudará en auditorías futuras.
